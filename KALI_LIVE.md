# Запуск в Kali Linux Live

Скрипт работает внутри уже загруженной Kali Live. Он **не создаёт загрузочную флешку**, не размечает диски и не извлекает хеши. Проверяйте только свои системы или системы, для которых у вас есть разрешение. Для запуска с Ventoy см. [отдельную пошаговую инструкцию](VENTOY_KALI.md).

## 1. Выберите место для данных

В Kali Live системный раздел загрузочной флешки часто доступен только для чтения, а изменения в оперативной памяти пропадают после перезагрузки. Используйте один из вариантов:

- отдельную подключённую флешку с доступным для записи разделом;
- существующий доступный для записи раздел на той же физической флешке, с которой запущена Kali;
- каталог в **уже настроенной** persistence, если система загружена в соответствующем режиме и вы проверили, что изменения сохраняются.

Узнать устройства и точки монтирования без изменения дисков:

```sh
lsblk -o NAME,SIZE,FSTYPE,LABEL,MOUNTPOINTS
```

Выберите свой каталог на смонтированном разделе. Ниже `/media/kali/AUDIT` — **пример**, фактический путь может отличаться:

```sh
DATA="/media/kali/AUDIT"
findmnt -T "$DATA" -o TARGET,SOURCE,FSTYPE,OPTIONS
```

Убедитесь по выводу, что выбран правильный носитель и раздел смонтирован для записи (`rw`). Не форматируйте и не изменяйте разделы наугад. Если всё на одной флешке, не извлекайте её, пока Kali с неё работает.

Если вместо отдельного раздела используется **уже проверенная** persistence, можно создать каталог в домашней папке и выбрать его:

```sh
mkdir -p "$HOME/audit-data"
DATA="$HOME/audit-data"
findmnt -T "$DATA" -o TARGET,SOURCE,FSTYPE,OPTIONS
```

Само создание каталога не означает, что persistence включена: без неё он может оказаться во временном слое.

`--check` проверяет запись временного файла и по возможности показывает тип файловой системы. Он предупреждает о `tmpfs` и `overlay`, но **не проверяет**, включена ли persistence, останутся ли файлы после перезагрузки и является ли выбранный каталог именно флешкой. Сохранность persistence можно отдельно подтвердить тестовым файлом и перезагрузкой.

## 2. Подготовьте программы и файлы

Нужны Python 3.9+, Hashcat 6.2.6+ и рабочий вычислительный backend. Проверьте в терминале:

```sh
python3 --version
hashcat --version
hashcat -I
```

В выводе `hashcat -I` должно быть доступное устройство. Для `--cpu` нужен OpenCL-драйвер CPU; для GPU — совместимый драйвер GPU. Наличие устройств зависит от оборудования и сборки Kali Live.

Если программ или CPU OpenCL нет и разрешено подключиться к репозиториям Kali, их можно установить вручную:

```sh
sudo apt update
sudo apt install python3 hashcat
sudo apt install pocl-opencl-icd  # только если нужен OpenCL CPU
```

Без настроенной persistence установленные в Live-систему пакеты после перезагрузки обычно исчезают. Команды установки скрипт не выполняет. Если используете отдельную сборку Hashcat на носителе, ей также нужны соответствующие модули и файлы.

Скопируйте в `"$DATA"` файлы:

- `usb_audit.py` из этого проекта;
- `crack_with_hint.py` рядом со скриптом, если нужен сценарий с подсказкой;
- `hashes.txt` — уже извлечённые хеши одного известного формата;
- `wordlist.txt` — свой словарь кандидатов, по одному на строку. Он не нужен при использовании встроенного списка `--weak`.

Не размещайте реальные хеши и пароли в чате. Проверить наличие основных файлов, не выводя их содержимое:

```sh
ls -lh "$DATA/usb_audit.py" "$DATA/hashes.txt"
# Если используете свой словарь:
ls -lh "$DATA/wordlist.txt"
```

## 3. Проверка окружения и запуск

Сначала проверьте каталог данных и Hashcat. Эта команда не запускает проверку хешей:

```sh
python3 "$DATA/usb_audit.py" --usb "$DATA" --check
```

Если Hashcat лежит на носителе, а не в `PATH`, задайте путь относительно `"$DATA"`, например:

```sh
python3 "$DATA/usb_audit.py" --usb "$DATA" --hashcat hashcat/hashcat --check
```

При сообщении о read-only или недоступной записи выберите другой доступный для записи раздел. При `overlay` убедитесь, что настроена и действительно работает persistence. `--check` не проверяет OpenCL и наличие входных файлов: для оборудования используйте `hashcat -I`, а файлы проверьте командой выше.

Пример проверки **NTLM** по своему `wordlist.txt` на CPU OpenCL:

```sh
python3 "$DATA/usb_audit.py" --usb "$DATA" --mode 1000 --cpu
```

Вместо своего словаря можно использовать небольшой встроенный список простых паролей. Следующая команда при совпадении показывает **пароль и хеш в терминале**:

```sh
python3 "$DATA/usb_audit.py" --usb "$DATA" --mode 1000 --weak --show-passwords --cpu
```

Без `--show-passwords` пароли не показываются. `--weak` и `--wordlist` несовместимы; подробности и ограничения встроенного списка приведены в [README.md](README.md). Вывод терминала может записываться другими программами — ограничьте к нему доступ.

Для одного подготовленного NTLM-хеша можно запустить последовательный сценарий с подсказкой:

```sh
python3 "$DATA/usb_audit.py" hint --usb "$DATA" --mode 1000 --hashes hashes.txt \
  --mask '?d?d?d?d' --runtime 600 --cpu
```

Рядом с `usb_audit.py` должен находиться `crack_with_hint.py`; файл `hashes.txt` в этом сценарии должен содержать одну непустую запись. Подсказка запрашивается скрыто. По порядку проверяются сама подсказка, мутации правилами Hashcat, словарь и указанная маска; совпадение выводится в терминал и останавливает дальнейшие этапы. Ограничение `--runtime` задаётся на каждый этап отдельно. Подробности и меры конфиденциальности — в [README.md](README.md).

Для GPU уберите `--cpu`, если Hashcat обнаружил подходящее устройство. Для `имя:хеш` добавьте `--username`. Если у вас другой формат, замените `1000` на подходящий режим из таблицы в [README.md](README.md); формат не определяется автоматически. Для обычного запуска права root не требуются, если пользователь может читать входные файлы и писать в каталог.

## 4. Результат

Результаты сохраняются в отдельный каталог `"$DATA"/audit-results/`. В обычном аудите `report.json` содержит статистику, а `matched-hashes.txt` — совпавшие хеши без паролей. При `--weak` туда также записывается весь встроенный список кандидатов без указания, какие из них совпали. Сценарий `hint` при необходимости сохраняет копию целевого хеша, правила и отчёт об этапах, но по умолчанию не сохраняет связь хеша с паролем. Флаг `--save-plaintext` явно включает сохранение такой связи в `cracked.txt`. При `--show-passwords` или использовании `hint` пароли намеренно показываются в терминале и могут попасть в его журналы. Исходные файлы не изменяются. Считайте весь каталог конфиденциальным и по возможности используйте шифрованный носитель.

Совпадение означает, что пароль найден в словаре. Отсутствие совпадения не доказывает стойкость. Проверьте `run_complete`, предупреждения Hashcat, отклонённые кандидаты и количество загруженных хешей. Перед безопасным извлечением **отдельного** носителя завершите проверку и размонтируйте его через интерфейс Kali. Если это загрузочная флешка, не извлекайте её во время работы Live-системы.

В текущей рабочей среде сама загрузка Kali Live, конкретные драйверы и persistence не проверялись; их нужно проверить на целевом компьютере.

## Находки

### F-01 — Браузер может обойти туннель: `network.proxy.failover_direct` не выставлен (High)

`app/user.js:5-9` включает SOCKS и remote DNS, но не трогает `network.proxy.failover_direct`. В Firefox/LibreWolf этот преф **по умолчанию `true`** (появился в FF91): при недоступном прокси системные запросы уходят прямым соединением. Это ровно тот случай, когда Xray умер, а браузер ещё жив.

- **Триггер:** Xray упал / порт 10808 занят / прокси-соединение сброшено; до срабатывания kill-switch (интервал 5 с, проверка IP раз в 30 с) браузер выполняет системный запрос — проверка связности, OCSP, обновление, captive-portal.
- **Последствие:** запрос уходит с реального IP колледжной сети мимо туннеля. Это и есть утечка, которую комплект обещает исключить.
- **Доказательство:** [Bugzilla 1207798](https://bugzilla.mozilla.org/show_bug.cgi?id=1207798) (преф добавлен в FF91 со значением `true`), [arkenfox/user.js #1247](https://github.com/arkenfox/user.js/pull/1247) и [#1251](https://github.com/arkenfox/user.js/issues/1251) — в профилях, работающих только через прокси, его выставляют в `false`.
- **Исправление:** в `user.js` добавить
  ```js
  user_pref("network.proxy.failover_direct", false);   // без прокси — не ходить вообще
  user_pref("network.http.http3.enable", false);       // QUIC идёт по UDP мимо SOCKS
  user_pref("network.proxy.allow_hijacking_localhost", true);
  ```
- **Проверка:** в браузере `about:config` → `network.proxy.failover_direct` = `false`; затем вручную `Stop-Process -Name xray -Force` и попытка открыть сайт — должна быть ошибка прокси, а не загрузка страницы.

### F-02 — Kill-switch без прав администратора не фильтрует трафик, а только закрывает процессы (High)

`start.ps1:257-260` ставит firewall-правила **только если** `$admin = true`; в противном случае `Breach()` делает `Stop-Process` для `librewolf/firefox/xray`. Защита в этот момент держится не на firewall, а на том, что в профиле прописан прокси.

- **Триггер:** любая ситуация, где браузер не идёт через прокси (F-01, ручная правка `about:config`, падение прокси-соединения).
- **Последствие:** watchdog этого **не увидит**: он проверяет туннель (`start.ps1:236` — `curl --socks5-hostname 127.0.0.1:10808`), а не браузер. Пока Xray жив, проверка IP всегда «чистая», даже если браузер в этот момент льёт напрямую.
- **Исправление:** (1) F-01 — обязательно; (2) добавить проверку владельца порта (F-04); (3) при наличии прав ставить правила **до** запуска браузера: outbound-deny для `LibreWolf.exe` и разрешение только на `127.0.0.1:10808`; (4) в README прямо написать: без прав администратора kill-switch = «закрыть браузер по таймеру», а не «заблокировать пакеты».
- **Проверка:** `Get-NetFirewallRule -DisplayName 'LibreWolf-USB*'`; тест из §4 брифа (`-KillTest`).

### F-03 — Firewall-правила не удаляются никогда: следующий запуск будет сломан (High)

`start.ps1:257-260` создаёт `LibreWolf-USB-KILLSWITCH` и `-XRAY` (Block, Outbound, по программе). Ни `start.ps1`, ни `clean-traces.ps1` их не снимают — `grep Remove-NetFirewallRule` по всему комплекту пуст.

- **Триггер:** один запуск от администратора, в котором сработал kill-switch.
- **Последствие:** правила остаются на машине навсегда и блокируют `LibreWolf.exe` и `xray.exe` даже при полностью рабочем VPN. Пользователь видит «VPN поднялся, браузер не открывает сайты» и не понимает причину. На «грязном ПК» это ещё и лишний постоянный след комплекта.
- **Исправление:** в начале `start.ps1` и в конце `clean-traces.ps1`:
  ```powershell
  Remove-NetFirewallRule -DisplayName 'LibreWolf-USB-KILLSWITCH*' -ErrorAction SilentlyContinue
  ```

### F-04 — Порт 10808 не аутентифицирован, «готовность» проверяется без владельца (Medium)

`start.ps1:48-54` (`Test-Socks`) считает туннель поднятым, если **кто-то** слушает `127.0.0.1:10808`.

- **Триггер:** на «грязном ПК» порт уже занят другим процессом (чужой прокси, вредонос, забытый Xray прошлой сессии) либо Xray не смог забиндиться, а старый слушатель остался.
- **Последствие:** скрипт считает туннель готовым и запускает браузер. Дальше два варианта: `Get-ExtIP` покажет реальный IP (повезло, `Fail` сработает) или IP чужого прокси (не повезло — весь трафик студента идёт через неизвестный сервер, который видит SNI и может подменять HTTP).
- **Исправление:** сверять PID слушателя с процессом Xray:
  ```powershell
  $own = (Get-NetTCPConnection -LocalPort $Port -State Listen -ErrorAction SilentlyContinue).OwningProcess
  if ($own -and ($own -notcontains $XrayProc.Id)) { Fail "Порт $Port занят чужим процессом (PID $own) — не запускаюсь." }
  ```
  и вызывать эту проверку вместо/вместе с `Test-Socks`.

### F-05 — Реальный IP пишется в лог на флешку, хотя комментарий утверждает обратное (Medium)

`start.ps1:122`: `Log "прямой IP: $RealIP (только в памяти)"` → `Log` делает `Add-Content` в `vpn\logs\session-*.log`.

- **Последствие:** секрет (реальный IP пользователя/сети) лежит открытым текстом на носителе; при потере или копировании флешки утекает вместе с `config.json`. Комментарий «только в памяти» вводит в заблуждение того, кто будет код читать.
- **Исправление:** логировать факт, а не значение: `Log "прямой IP определён (скрыт)"`; при необходимости — маска `1.2.x.x`.

### F-06 — `xray.exe` скачивается и запускается без проверки целостности (Medium)

`prepare-home.ps1:97-105`: `api.github.com/.../releases/latest` → `browser_download_url` → `curl` → `tar -xf` → сразу исполняется в `start.ps1`. Ни хеша, ни подписи, ни пина версии. Для LibreWolf проверка sha256 хотя бы пытается выполниться, для исполняемого файла, который станет вашим туннелем, — нет.

- **Триггер:** компрометация релиза/аккаунта upstream, MITM на домашнем канале (HTTPS спасает, но `curl` без `--proto '=https'` и без `--tlsv1.2`), подмена файла в `_download\` (скрипт использует уже лежащий zip, если он > 20 МБ — но для Xray такой ветки нет, файл всегда качается).
- **Последствие:** произвольный код с правами пользователя, который получит VLESS-UUID и весь трафик.
- **Исправление:** пиновать версию (`v25.x.y`), брать хеш из GitHub API (`asset.digest` = `sha256:...`) или из `*.sha256`-файла релиза, сверять `Get-FileHash`, при несовпадении — `Fail`. Добавить `curl.exe --proto '=https' --tlsv1.2 -L --fail`.

### F-07 — Проверка sha256 для LibreWolf фактически необязательна и может проверять не тот файл (Medium)

`prepare-home.ps1:64-74`: URL контрольной суммы строится от `$candidates[0]`, а скачивание идёт из любого кандидата (`foreach ($u in $candidates)`), включая asset-ссылку из GitLab API. Если `.sha256sum` не скачался (`$LASTEXITCODE -ne 0`), блок `if` просто не выполняется — **проверки нет и сообщения об этом нет**.

- **Последствие:** либо проверяется хеш другого файла (ложный «sha256 НЕ СОВПАЛ» на исправном архиве), либо не проверяется ничего (ложное спокойствие).
- **Исправление:** помнить фактический `$u`, с которого скачали; требовать checksum (`Fail`, если недоступен); сверять с `$actual` именно этого файла.

### F-08 — JSON собирается конкатенацией: `JsonEsc` экранирует только `\` и `"` (Medium)

`vless-lib.ps1:5-8` — `JsonEsc` не трогает переводы строк, табы и `\u0000-\u001f`; `alpn` подставляется вообще без экранирования (`vless-lib.ps1:105` — `($Node.alpn -replace ',', '","')`).

- **Триггер:** ссылка `vless://` или подписка, где в `sni/host/path/alpn` есть перевод строки, таб или кавычки.
- **Последствие:** битый `config.json`; в лучшем случае скрипт поймает это проверкой `ConvertFrom-Json` в `start.ps1` и откажется стартовать, в худшем — Xray стартует с не тем, что задумано (подмена полей структуры).
- **Исправление:** не собирать JSON строками. Собрать `[ordered]@{}` и отдать `ConvertTo-Json -Depth 10`, либо расширить `JsonEsc` до полного набора escape-последовательностей (`\n`, `\r`, `\t`, `\u00XX`) и применять его к `alpn` и остальным значениям.

### F-09 — `-Deep` чистит чужие следы: UserAssist для `cmd/powershell` и Prefetch `FIREFOX*.pf` (Medium)

`clean-traces.ps1:79` удаляет `FIREFOX*.pf` (это может быть Prefetch чужого Firefox), а `clean-traces.ps1:126` при `-Deep` удаляет записи UserAssist для **любых** запусков `cmd.exe`/`powershell.exe`, не только ваших.

- **Последствие:** побочный ущерб на общей машине (стирается диагностическая история других людей) и рост заметности: администратор видит не «студент запускал скрипт», а «кто-то вычистил историю запусков cmd/powershell» — это более подозрительно, чем исходный факт.
- **Исправление:** ограничиться строго своими записями (по маркеру `librewolf|xray|LibreWolf-USB`, в том числе в путях флешки), `FIREFOX*.pf` убрать или проверять, что путь в Prefetch ведёт на флешку.

README честно перечисляет Event Log и Prefetch для `CMD/POWERSHELL`, но не упоминает:

| --- | --- | --- |

### F-11 — Watchdog проверяет живость по PID (Low)

`start.ps1:280`: `Get-Process -Id $s.xrayPid`. При переиспользовании PID (Xray умер, PID достался другому процессу) watchdog считает туннель живым. Проверять дополнительно имя и путь процесса.

### F-12 — `Get-ExtIP` до туннеля — единственный прямой запрос наружу (Low)

`start.ps1:36-46,120-122` до поднятия туннеля стучится на `api.ipify.org` и `ifconfig.me` (и резолвит их через DNS колледжа). Формально это противоречит «весь трафик через VPN», хотя утечкой трафика не является. Плюс см. F-05.

### F-13 — Подмена клиента подписки — вопрос ToS провайдера, не безопасности (Info)

`update-sub.ps1:21`, `vless-lib.ps1:209,227` и `update-sub.py:69` отправляют `User-Agent: INCY/3.0.28` и `x-hwid`, чтобы в панели провайдера устройство не отображалось как подключённое (README подаёт это как фичу). Это обход учёта устройств у сервиса: технически безобидно, но может нарушать его правила. Решение за владельцем подписки; в README лучше назвать это честно.

### F-14 — Расхождение PS- и Python-версий по возможностям (Low)

`update-sub.py` не поддерживает `httpupgrade`, `spx`, `tcp+http header`, `headerType`; при подписке с такими узлами Python-версия молча соберёт другой (нерабочий) конфиг. Либо выровнять, либо в README указать, что Python-версия — резервная и неполная.

### F-15 — Строковая интерполяция съедала расширение: бэкап конфига писался в `.json` (Medium, найдено при исправлении F-08)

В PowerShell внутри двойных кавычек `$var.name` — это **доступ к свойству**, а не «переменная, потом точка». Поэтому `"$Cfg.bak.json"` вычисляется как свойство `bak` у строки `$Cfg` (его нет → пустая строка) плюс литерал `.json`. Итог: `Copy-Item $Cfg "$Cfg.bak.json"` писал бэкап в файл с именем `.json` в **текущем каталоге**, а не в `vpn\config.bak.json`, как написано в README; откат читал тот же `.json`. Так же `$LogFile = Join-Path $Logs "session-$Ts.log"` давало `session-.log`: все сессии писались в один файл без даты.

- **Последствие:** «старый конфиг сохранён» — ложь; при запуске из другого каталога откат мог подхватить посторонний `.json`; логи не разделены по сессиям.
- **Исправление:** явная конкатенация во всех пяти местах: `($Cfg + '.bak.json')`, `($OutFile + '.bak.json')`, `("session-$Ts" + '.log')`, `($xz + '.sha256')`.

### F-16 — `New-Object System.Collections.Generic.List[object]` + `@()` ломал `ConvertTo-Nodes` (High, найдено реальным прогоном)

В переписанной библиотеке (F-08/F-14) узлы копились в `List[object]`, а возвращались
через `@($nodes)`. Под реальным `pwsh 7.7.0` (Linux, .NET 11) это падает с
`System.ArgumentException: Argument types do not match` — причём на **любом** списке,
даже пустом: `New-Object` создаёт `List<System.Object>` из другой сборки, и приведение
к массиву не сходится по типам. Под Windows PowerShell 5.1 этот конкретный сбой
не воспроизведён (проверить негде), но конструкция ненадёжна по определению.

**Последствие:** `ConvertTo-Nodes` падал у всех вызывающих — то есть обновление
подписки (`update-sub.ps1`) и авто-обновление в `start.ps1` не работали бы вовсе.
Это регресс, внесённый моей же правкой в архиве, который я отдал пользователю.

**Исправление:** `Generic.List` убран совсем — обычный массив `@()` и `+=`
(в `New-Outbound`/`New-ConfigJson`, `ConvertTo-Nodes`, `vless-to-config.ps1`).
Проверено прогоном: 36/36 в `self-check`, 7/7 в сквозных сценариях.

### F-17 — `ConvertTo-Nodes` не понимал base64-тело подписки (Low, найдено прогоном)

Декодирование base64 жило только в `Get-SubBody` (сетевая функция). Если тело
подписки приходило в base64 иным путём, `ConvertTo-Nodes` молча возвращал 0 узлов,
и пользователь видел «в подписке не нашлось валидных ссылок» при валидной подписке.

**Исправление:** `ConvertTo-Nodes` сам распознаёт base64 (в т.ч. url-safe и без
паддинга). Проверено: base64-подписка из 7 ссылок даёт 7 серверов.

### Замечание к самому себе

Мои первые проверки в `self-check.ps1` требовали правил `direct`/`block` в `routing`.
Это было неверно: в исходном комплекте таких правил нет и не было — весь трафик идёт
через `balancerTag`, а `direct`/`block` объявлены, но не используются (это и есть
«прямого пути наружу нет»). Утверждения исправлены на фактическое поведение.

### F-18 — Кириллические имена в архиве превращались в кракозябры (Low, нашёл пользователь)

Архив собирался утилитой `zip` в Linux-локали без UTF-8. Info-ZIP в таком случае
кладёт имена файлов «сырыми байтами» и **не выставляет general-purpose bit 11**
(«имена в UTF-8»). Windows Explorer этот бит уважает, а без него декодирует имена
как CP1251 — отсюда `РџРѕРґРіРѕС‚РѕРІРєР°-Р”РћРњРђ.bat`, `Р§РРЎРўРљРђ.bat`,
`РџР РћР’Р•Р РљРђ.bat`.

**Последствие:** функционально ничего не сломалось (внутри `.bat` пути латиницей,
`START.bat` вообще ASCII), но человек видит мусор вместо названий и не понимает,
что запускать.

**Исправление:** архив собирается `tests/build-zip.py` (Python `zipfile` кодирует
имена в UTF-8 и ставит флаг), а сборщик ещё и проверяет бит 0x800 у каждого
не-ASCII имени и падает, если его нет. Проверено чтением архива: у всех трёх
кириллических записей флаг выставлен.

### F-19 — Пропавший `app\user.js` давал технический сбой вместо отказа (Medium, найдено прогоном)

`start.ps1` просто копировал `app\user.js` в профиль. Если файла нет (антивирус
забрал, неполная распаковка, копирование «только .bat») — скрипт падал сырой ошибкой
`Copy-Item: Cannot find path ...`. Опасность в том, что `user.js` — единственное, что
зашивает `network.proxy.socks` в браузер: без него браузер пошёл бы напрямую.

**Исправление:** явная проверка перед копированием — `Fail "Нет app\user.js — без
него браузер пойдёт мимо прокси"`. Проверено в двух прогонах: без файла — понятный
отказ, с файлом — работа продолжается.

## Что сделано хорошо

- Порядок запуска правильный: туннель → проверка внешнего IP → только потом браузер; при совпадении с реальным IP браузер не стартует (`start.ps1:138-141`).
- В маршрутизации Xray **нет** `direct`-fallback: всё уходит в балансировщик, `freedom` объявлен, но не используется (`vless-lib.ps1:155,197`).
- Inbound'ы только на `127.0.0.1`, SOCKS `noauth` — наружу не выставлено.
- Многосерверный `leastPing` + `observatory`, бэкап `config.bak.json` и откат при неудачном обновлении подписки через туннель — сделано аккуратно, с повторной проверкой IP.
- `user.js`: `socks_remote_dns=true`, WebRTC off, disk cache off, session restore off, fxaccounts off, no password saving — ровно то, что нужно для чужого ПК.
- `.ps1` сохранены с UTF-8 BOM — PowerShell 5.1 не превратит кириллицу в мусор (проверено: BOM есть во всех шести файлах).
- В README есть раздел «что остаётся» — редкость; его нужно расширить (F-10), а не убирать.

### Что из 12 пунктов не закрыто кодом

- **Пункт 1 (подмена файлов на чужом ПК).** `robocopy /MIR` из домашней мастер-копии
  помогает между поездками, но внутри поездки не спасает: подменить `vpn\config.json`
  на чужой валидный сервер с настоящим TLS можно так, что ничего не упадёт —
  линтер увидит корректный конфиг. Ловится только аппаратной защитой от записи
  и печатью SHA-256 (отложено пользователем).
- **Пункт 9 (загрузки в `Downloads`).** Папку загрузок и «следы» профиля надо
  разводить отдельной правкой; в этой волне не трогалось, чтобы не менять
  привычное поведение браузера.
- **Пункт 11 (отзываемый ключ).** Требует второго носителя/DPAPI — отложено.
